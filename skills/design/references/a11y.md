# Accessibility reference — thresholds and checklists

This file alone owns the WCAG numbers and accessibility checks. Skills point here
and never repeat the thresholds. The target is **WCAG AA** unless the user says
otherwise.

Accessibility is the floor, not the ceiling — even a borderline miss (contrast at
4.4:1) gets fixed.

## Contrast

| Element | Minimum ratio |
|---|---|
| Normal text (under 18px) | **4.5:1** |
| Large text (18px+ bold, or 24px+) | **3:1** |
| UI components — buttons, icons, focus rings | **3:1** |

For every color pair you can resolve, compute the real ratio, and report it next
to the required minimum instead of a bare "fails". Confirm with the WebAIM
contrast checker or something equivalent.

**Signaling by color alone fails.** Examples: green/red with no icon, links with
no underline, charts with neither legend nor direct labels. Add a second signal —
icon, text, or position. ~8% of men have some colorblindness, and grayscale or
high-contrast modes need that second signal as well.

## Semantic HTML

Choose the element that matches the job — assistive tech reads the page through
its semantic elements. **ARIA is a patch**: add it just where plain semantic HTML has no way to express the role.

- `<button>` for buttons, never `<div onclick>`
- `<a href>` for links, never a styled `<div>`
- `<label for="…">` bound to `<input id="…">`
- `<nav>`, `<main>`, `<article>`, `<section>`, `<aside>` for landmarks
- Exactly one `<h1>`; no skipped heading levels; headings describe content, not
  visual size
- Flag `role="button"` on a `<div>` that could simply be a `<button>`

**Every meaningful image gets alt text** that says what the image conveys
(`alt="Wireless headphones, side view"`, not `alt="product"`). Purely decorative
images take `alt=""` so screen readers pass over them.

## Keyboard and focus

- **Anything clickable can be reached with Tab.** Menus that open only on hover,
  dropdowns usable only with a mouse, and modals the keyboard can't operate fail
  outright.
- **Tab order that makes sense**, tracking the reading order. Flag any `tabindex` > 0.
- **Interaction patterns:** Escape closes modals; Enter/Space opens dropdowns and
  arrow keys move through them; Enter inside a field submits the form.
- **Visible focus rings.** Removing the outline (`outline: none`) without a visible substitute is among the most frequent accessibility failures. Prefer `:focus-visible` to bare `:focus`; use at least 2px thickness, 2px offset, and 3:1 against the adjacent
  background.

```css
button:focus-visible {
  outline: 2px solid var(--primary);
  outline-offset: 2px;
}
```

- **Skip links** ("Skip to main content") belong on pages where the same nav repeats heavily.

## Motion

Honor `prefers-reduced-motion` for any motion longer than a couple hundred ms:

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```

**Never flash more than 3 times per second** — faster rates can provoke photosensitive seizures. Any content that flashes must come with a pause control.

## Forms

- Errors are **specific** — "Email address is invalid", not "Invalid"
- Each error is linked to its field, visually *and* through `aria-describedby`
- Mark required fields through text and/or an icon together with the `required` attribute; color must never be the only cue
- Every input has a `<label>` (or `aria-label`); **a placeholder is not a
  label** — it vanishes once the user starts typing
- Use `type="email"`, `type="tel"`, and `autocomplete` attributes so autofill and
  mobile keyboards behave correctly

## Interactive states

Each interactive element needs all of these states. If one is absent, the element seems broken: a button lacking hover resembles a label, and one without a focus ring is unusable by keyboard.

| State | Requirement |
|---|---|
| **Default** | Obviously interactive while idle — a fill or border that sets it apart from body text. Anything that shows it's interactive only on hover fails touch and keyboard users. |
| **Hover** | A visible shift when the cursor is over it: color, background, or border. Add lift and shadow only if the brand's motion mode asks for them — a hover lift on every card is a tell. Don't lower the opacity; that reads as disabled. |
| **Active / pressed** | A darker color or `transform: scale(0.98)` — it shows the click registered before the action finishes. |
| **Focus** | As set out in the keyboard section above. |
| **Disabled** | ~0.6 opacity, no hover effect, `cursor: not-allowed`, and visually unlike both default and hover. When it's disabled until some condition is met, say *why*. |
| **Loading** | Block repeat clicks by disabling on press, show a spinner or "Loading…" in place of the label, and bring the label back afterward. Content loaded while rendering shows a placeholder skeleton or a progress indicator. |

Fallback values for when the design system defines none: hover 10–15% darker
(or `color-mix`), active a further 10%, disabled opacity 0.6, focus
`outline: 2px solid var(--color-primary); outline-offset: 2px`, transition
`0.2s ease`.

## Feedback and state visibility

Each action must produce a visible outcome: success (toast, inline confirmation,
or redirect with confirmation), failure (a clear error, attached to the field if
the problem is field-specific), validation (shown on blur or submit, cleared once
fixed), state change (an immediate visual update). **Flag silent successes and
silent failures — both feel broken.**

Users must be able to see where they are, so mark the current page or tab, the selected items, and any applied filter or sort so they stand apart from the rest. When everything looks alike, users
can't tell where they are.

## Hit targets

On touch surfaces, never go below **44×44px**.
